# 基于大数据计算引擎的在线判题系统的设计与实现

## 中文摘要
本文围绕“基于大数据计算引擎的在线判题系统的设计与实现”展开研究，设计并实现了一套面向教学与训练场景的在线判题平台。系统后端采用 Spring Boot 构建，负责用户认证、题目管理、测试用例管理、代码提交、判题任务调度和结果查询；MySQL 用于保存业务数据与分析结果；Docker 用于构建多语言判题沙箱，为 C、C++、Java 和 Python 提供隔离的编译与运行环境；前端采用 React、TypeScript、Ant Design 和 ECharts 实现普通用户与管理员的可视化页面。

在数据分析方面，系统构建了“业务数据库—HDFS—Hive/Spark—MySQL—前端页面”的离线处理链路。每次判题完成后，系统将提交事件写入分析事件表，再导出到 HDFS。Hive 负责完成全站汇总、题目统计、用户统计、语言分布、结果分布和小时活跃度等描述性分析；Spark 在此基础上进一步实现未来提交量预测和题目难度评估，并将结果回写 MySQL，供后台页面直接查询与展示。

研究结果表明，该系统能够较完整地实现在线判题、离线分析、预测评估和可视化展示的闭环，说明将 Hadoop、Hive 和 Spark 引入在线判题平台具有实际可行性，并能够为教学分析、题库建设和系统优化提供有效支撑。

**关键词**：在线判题系统；Spring Boot；Docker；Hadoop；Hive；Spark；数据分析；难度评估

## Abstract
This thesis studies the design and implementation of an online judge system based on big data computing engines. A complete platform for teaching and programming training is designed and implemented. The backend is built with Spring Boot and is responsible for user authentication, problem management, testcase management, code submission, judging task scheduling, and result query. MySQL is used to store both business data and analysis results. Docker is adopted as the judging sandbox to provide isolated compilation and runtime environments for C, C++, Java, and Python. The frontend is implemented with React, TypeScript, Ant Design, and ECharts to provide visualization pages for ordinary users and administrators.

For data analysis, the system constructs an offline processing pipeline of “business database - HDFS - Hive/Spark - MySQL - frontend pages”. After each judging task is completed, the system writes an event record into the analysis event table and then exports it to HDFS. Hive is used to produce descriptive statistics such as platform-wide summaries, problem-level statistics, user-level statistics, language distribution, verdict distribution, and hourly activity. On top of that, Spark is introduced to implement future submission forecasting and problem difficulty assessment. The generated results are written back to MySQL so that the backend APIs and frontend pages can query them directly.

The implementation shows that the system can form a complete closed loop covering online judging, offline analysis, predictive evaluation, and visualization. The results indicate that integrating Hadoop, Hive, and Spark into an online judge platform is technically feasible and can provide effective support for teaching analysis, problem-set construction, and system optimization.

**Key Words**: online judge system; Spring Boot; Docker; Hadoop; Hive; Spark; data analysis; difficulty assessment

# 第一章 绪论

## 1.1 研究背景
随着计算机科学教育的普及和信息化教学模式的发展，程序设计课程已经成为高校计算机类专业的重要基础课程。与传统理论课程相比，程序设计课程更加依赖实验、练习和持续反馈。学生只有通过不断编写代码、运行程序和修正错误，才能逐步掌握数据结构、算法设计、程序调试和复杂问题求解能力。在这一背景下，在线判题系统因其能够提供自动化代码评测、即时反馈和题库管理能力，已经被广泛应用于教学实验平台、课程作业系统、校内选拔赛和算法竞赛训练平台之中。

在线判题系统的核心任务是对用户提交的程序进行编译、执行和输出校验，并根据题目测试数据给出接受、错误答案、运行错误、超时、内存超限等结果。一个设计良好的在线判题系统能够显著提高教师批改效率，减轻人工检查负担，并为学生提供及时反馈。然而，随着系统规模扩大和运行周期增加，单纯实现“提交—判题—返回结果”这一业务闭环已经难以满足教学与管理的综合需求。平台运营者和教师希望进一步了解学生整体提交趋势、不同题目的难度差异、常见错误类型、各语言使用情况以及系统在不同时间段的负载分布，以便优化教学安排、改进题库设计和提升平台稳定性。

另一方面，近年来 Hadoop、Hive、Spark 等大数据计算框架已经在海量数据存储、批处理分析和预测建模领域得到了广泛应用。在线判题系统在长期运行过程中会积累大量结构化日志，包括提交编号、用户编号、题目编号、编程语言、判题结果、运行时间、内存占用以及提交时间等信息。这些数据具有明显的时序性、行为性和多维度特征，非常适合借助大数据计算框架进行离线统计与深度挖掘。如果能够将大数据计算引擎与在线判题系统有机结合，就可以实现从基础业务系统到数据驱动平台的能力提升，使系统不仅能够“完成判题”，还能够“理解判题数据”。

此外，随着容器技术的成熟，基于 Docker 的代码沙箱已经成为在线判题系统实现安全隔离的重要手段。相比传统直接在宿主机上执行用户代码的方式，Docker 能够提供更加清晰的环境隔离、资源限制和安全控制机制，有助于降低恶意代码、无限循环、异常进程扩散等问题对宿主机造成的风险。因此，将 Docker 判题、多语言支持、Hadoop 离线分析和 Spark 预测模块综合起来，形成一套完整的在线判题平台，既具有工程实现价值，也具备作为本科毕业设计研究对象的现实意义。

## 1.2 研究目的与意义
本文的研究目标是设计并实现一套基于大数据计算引擎的在线判题系统，在实现常规在线判题功能的基础上，进一步构建日志导出、离线统计、预测分析和可视化展示能力，从而形成集“业务执行、数据沉淀、统计分析、预测支撑”于一体的综合平台。

从教学角度看，在线判题系统能够帮助教师快速了解学生对课程知识点的掌握程度。通过统计不同题目的提交数量、通过率、错误分布和平均尝试次数，可以识别出学生普遍存在的问题，辅助教师调整教学内容和实验安排。从学生角度看，通过分析个人提交趋势、语言偏好、结果分布和最近提交记录，可以帮助学生更好地理解自身学习状态和薄弱环节，形成数据驱动的学习反馈。

从平台运营角度看，判题日志不仅反映用户行为，还反映系统负载情况和题库质量。通过对系统提交趋势、小时活跃度、语言分布和题目难度进行分析，可以更合理地安排资源、优化题库、定位异常题目，并基于历史数据构建未来趋势预测和题目难度评估模型。因此，本课题既具有工程应用意义，也体现了大数据计算技术在教育平台场景中的综合应用价值。

## 1.3 国内外研究现状
国外较早出现的在线判题平台主要服务于算法竞赛和程序设计训练，例如 UVa Online Judge、Codeforces、AtCoder、LeetCode 等。这些平台经过长期发展，在题库规模、评测性能、语言支持和用户体验方面较为成熟。其中，面向竞赛的平台更强调判题性能和高并发处理能力，面向刷题与面试的平台则更加重视题库组织、用户画像和学习路径设计。国外平台通常已经具备较强的数据分析能力，但相关实现细节大多没有公开，更多体现在推荐系统、题目难度标签和用户成长反馈等产品功能层面。

国内在线判题平台的发展也较快，既包括面向竞赛训练的系统，也包括高校课程实验平台。很多高校和培训机构基于开源系统进行二次开发，实现题目管理、代码提交和自动判题等功能。一些开源 OJ 系统如 HUSTOJ、QDUOJ 等，已经提供了较为完整的后端能力和判题逻辑，但在大数据分析与预测模块方面仍然相对薄弱，更多聚焦于业务本身。此外，部分在线教育平台虽然也具备一定的数据看板，但往往缺乏与大数据计算引擎深度结合的可复用架构。

从相关研究来看，现有工作更多集中在以下几个方面：一是安全判题机制，例如多语言隔离执行、资源限制和恶意代码防护；二是系统性能优化，例如任务队列、分布式判题和并发调度；三是程序评测算法与输出比对策略；四是学习行为分析和用户画像构建。相比之下，将 Docker 判题、Hadoop/Hive 离线分析和 Spark 预测模块整合到一个统一的在线判题系统中，并形成完整的数据产品链路的研究与工程实现仍然具有一定空间。

## 1.4 本文研究内容
本文围绕在线判题系统的实际需求，完成了以下几个方面的设计与实现工作。

第一，完成在线判题系统的基础业务模块设计与实现，包括用户注册登录、管理员与普通用户权限划分、题目管理、测试用例管理、代码提交、判题任务调度以及判题结果查询等功能，形成完整的业务闭环。

第二，采用 Docker 容器构建代码评测沙箱，支持 C、C++、Java、Python 等常见语言的编译与运行，并通过 CPU、内存、进程数和网络访问控制，实现较为安全的判题环境。

第三，构建判题事件数据链路。在每次代码评测完成后，系统将判题核心信息写入分析事件表，再导出到 HDFS，借助 Hive 实现基础聚合与描述性分析，包括全站提交统计、题目统计、用户统计、语言分布、结果分布、小时活跃度等内容。

第四，引入 Spark 作为预测与评估引擎。在已有 Hive 数据基础上，首先实现未来每日提交量预测，然后进一步实现基于历史判题行为的题目难度评估与标签生成，用以支撑管理员对题库质量和系统运行趋势的观察。

第五，基于前后端分离架构完成数据可视化页面建设，为普通用户提供个人提交趋势和行为统计，为管理员提供系统分析页、预测页以及题目难度评估页，实现分析结果的产品化呈现。

# 第二章 相关技术介绍

## 2.1 Spring Boot 框架
Spring Boot 是基于 Spring 生态体系构建的快速开发框架，具有自动配置、依赖管理和内嵌 Web 容器等特点，能够显著降低 Java Web 应用的开发与部署复杂度。在本系统中，Spring Boot 被用于构建整个业务后端，包括用户管理、题目管理、提交处理、判题任务调度、分析结果查询以及认证授权等功能模块。

选择 Spring Boot 的主要原因有三点。其一，Spring Boot 的分层结构清晰，易于组织 Controller、Service、Repository 和 Entity 等模块，适合构建功能相对完整的单体系统。其二，Spring Data JPA 提供了方便的数据访问方式，能够快速实现对 MySQL 中业务表和分析结果表的增删改查。其三，Spring Security 与 JWT 机制集成方便，能够较好地支持普通用户和管理员的角色区分。

在系统实现中，Controller 层负责接收前端请求并进行参数校验；Service 层负责业务逻辑处理，如提交生成、判题执行、分析结果封装；Repository 层依靠 JPA 或原生查询访问数据库；实体类负责映射 MySQL 表结构。这样的架构层次便于维护和扩展，也为后续新增分析 API 和预测 API 提供了良好基础。

## 2.2 MySQL 数据库
MySQL 是一种广泛应用的关系型数据库管理系统，具有部署简单、使用成熟、事务支持良好等特点。在本系统中，MySQL 既承担业务数据存储，也承担分析结果回写后的查询支撑。业务数据包括用户、题目、测试用例、提交、判题任务、判题结果和分析事件；分析结果数据包括按天汇总的统计表、描述性分析结果表、提交量预测表以及题目难度评估表。

将 MySQL 作为业务数据库具有明显优势。首先，业务数据天然是结构化的，适合用关系模型建模。其次，MySQL 与 Spring Boot 集成简单，事务管理完善。再次，离线分析结果回写到 MySQL 后，前端页面无需直接连接 Hive 或 Spark，只需通过后端 API 读取 MySQL 表即可，既降低前端复杂度，也减少大数据集群对在线查询的影响。

## 2.3 Docker 容器技术
在线判题系统需要执行用户提交的代码，而用户代码具有不可控性，可能包含恶意指令、无限循环、异常进程创建、资源占用失控等风险。因此，构建安全的代码执行沙箱是在线判题系统的关键问题之一。Docker 通过容器机制提供了进程级隔离能力，使得应用能够在相对独立的运行环境中执行，同时共享宿主机内核，具备较高的性能与易用性。

本系统使用 Docker 为不同语言构建独立镜像，例如 GCC 镜像、Java 镜像和 Python 镜像。每次判题时，系统将提交代码和测试数据挂载到容器内部工作目录，在容器内完成编译和运行操作，并通过禁用网络、限制 CPU、限制内存、限制进程数、只读根文件系统和临时目录挂载等方式控制执行环境。这样既保证了评测逻辑的一致性，又降低了用户代码对宿主机造成风险的可能性。

## 2.4 Hadoop HDFS
HDFS 是 Hadoop 生态中的分布式文件系统，用于存储海量数据，具有高吞吐和面向批处理分析的特点。本系统使用 HDFS 存储判题分析事件的离线文件。每次将 MySQL 中的分析事件导出后，系统会按照日期分区写入 HDFS 目录，例如 `/oj/analysis/dt=2026-04-01`。这种按天分区的方式有利于后续 Hive 和 Spark 按日期读取与计算。

引入 HDFS 的原因在于，判题日志属于典型的可累计历史数据，适合长期沉淀并供离线分析使用。若直接在业务数据库中长时间堆积大量明细日志，会影响在线查询和业务事务性能，而 HDFS 更适合承担历史原始数据存储职责。

## 2.5 Hive 数据仓库技术
Hive 是构建在 Hadoop 之上的数据仓库工具，能够通过类 SQL 的方式对 HDFS 上的数据进行查询和聚合，适合进行离线统计分析。本系统使用 Hive 完成基础日报统计和描述性分析任务，例如每日提交总量、按题目统计、按用户统计、语言分布、判题结果分布和小时活跃度分析。

系统通过创建外部表 `oj.analysis_events` 将 HDFS 中的判题日志目录映射为结构化表，再基于 Hive SQL 对数据进行聚合，并将结果写入 HDFS 的聚合目录，最后导回 MySQL。采用 Hive 的好处在于统计逻辑清晰，SQL 易读，维护成本较低，适合实现周期性、批量性的汇总分析任务。

## 2.6 Spark 大数据计算引擎
Spark 是一种通用的大数据计算框架，具有内存计算能力强、任务执行速度快、适合批处理和机器学习扩展的特点。本系统在已有 Hive 分析基础上，引入 Spark 承担更复杂的计算任务，主要包括提交量预测和题目难度评估。

相比 Hive 更擅长 SQL 聚合，Spark 在以下两方面更适合本系统：一是基于 DataFrame 和 SQL API 可以方便地对数据进行清洗、特征构造和复杂指标计算；二是 Spark MLlib 或自定义规则模型能够支持预测与评估模块的实现，使系统在传统统计之外具备趋势预测和难度评估能力。

## 2.7 React 前端技术栈
前端部分采用 React + TypeScript + Vite 的组合，使用 Ant Design 构建表单、表格和布局组件，使用 ECharts 完成统计图表展示。前端主要分为普通用户功能页和管理员功能页两类，包含题目列表、题目详情、提交结果页、用户分析页、管理员题目管理页、系统分析页、预测页和题目难度评估页。

之所以选择 React 技术栈，是因为其组件化开发方式便于页面拆分与复用，TypeScript 有助于统一接口类型约束，Ant Design 能够快速搭建后台风格界面，ECharts 则便于绘制折线图、柱状图、饼图和趋势图，从而直观展示离线分析和预测结果。

## 2.8 本章小结
本章介绍了系统建设所依赖的核心技术，包括 Spring Boot、MySQL、Docker、HDFS、Hive、Spark 以及 React 前端技术栈。上述技术在本系统中分别承担业务实现、安全判题、数据存储、离线计算、预测分析和可视化展示等职责，共同构成了“在线判题 + 大数据分析”的技术基础。

# 第三章 系统需求分析

## 3.1 系统目标分析
本系统的总体目标是构建一套面向教学与训练场景的在线判题平台，在实现常规题目管理和自动判题的基础上，进一步引入大数据分析和预测能力，使平台不仅能够评测代码，还能够沉淀并利用判题数据，为教师、管理员和学生提供更丰富的信息支持。

从用户视角来看，系统需要为普通用户提供注册、登录、查看题目、提交代码、查看判题结果以及查看个人分析数据等功能；为管理员提供题目管理、测试用例管理、导出判题日志、查看全站分析结果和预测结果等功能。

从系统视角来看，平台需要具备安全、稳定和可扩展特性。判题部分必须隔离执行环境，避免用户代码对宿主机造成影响；数据分析部分必须能够处理不断累积的历史数据，并以较低成本生成统计结果；预测模块则需要建立在已有数据沉淀基础之上，输出对管理决策有价值的信息。

## 3.2 功能需求分析
### 3.2.1 用户管理需求
系统应支持用户注册与登录。用户注册时需要提交用户名和密码；登录后应获取令牌，用于访问受保护接口。系统应区分普通用户和管理员权限，普通用户主要用于题目浏览、代码提交与个人分析查看，管理员则额外具备题目管理、测试用例管理、分析导出与后台统计查看权限。

### 3.2.2 题目管理需求
管理员应能够新增题目、修改题目标题与描述、配置时间限制和内存限制，并管理题目对应的测试用例。测试用例管理包括新增、覆盖和删除。普通用户能够查看题目基本信息，但不能查看测试用例内容。

### 3.2.3 代码提交与判题需求
普通用户在选择题目后，应能够提交代码并指定编程语言。系统收到提交后，需要异步创建判题任务，将用户代码在 Docker 容器中完成编译与运行，并与标准输出进行比较，返回 AC、WA、RE、CE、TLE 等判题结果。用户能够查询提交状态与判题详情。

### 3.2.4 日志分析需求
系统应在每次判题完成后记录分析事件，形成包含用户、题目、语言、判题结果、运行时间、内存使用和时间戳等信息的日志数据。管理员应能够触发日志导出到 HDFS，并通过离线计算获得日报统计和专题分析结果，包括系统整体趋势、题目分析、用户分析、语言分布、结果分布和小时活跃度等。

### 3.2.5 预测与评估需求
系统除了提供描述性分析，还应具备一定的预测和评估能力。管理员应能够查看未来若干天提交量预测结果，用于观察平台负载趋势；同时应能够查看基于历史判题行为计算出的题目难度分数与难度标签，从而辅助题库管理和教学安排。

## 3.3 非功能需求分析
### 3.3.1 安全性需求
系统的安全性主要体现在两个方面：一是用户认证与权限控制，保证普通用户与管理员的功能边界清晰；二是判题执行安全，通过容器隔离、网络禁用、资源限制和目录权限控制，避免恶意代码影响宿主环境。

### 3.3.2 可靠性需求
判题任务属于系统核心业务，系统应保证提交后任务能够被稳定拉取和执行。对于运行中出现的异常，应具备重试能力和失败状态记录，避免任务长时间悬挂。同时，判题产生的工作目录应及时清理，以防止临时文件堆积。

### 3.3.3 可扩展性需求
题目类型、支持语言、分析指标和预测模型未来都可能增加。因此系统架构应尽量保持模块边界清晰，便于后续扩展更多语言镜像、增加新的 Hive 统计脚本或接入更复杂的 Spark 模型。

### 3.3.4 可维护性需求
由于本系统同时涉及后端业务、Docker 沙箱、Hadoop/Hive、Spark 和前端展示，必须通过清晰的目录结构、分层设计和相对独立的脚本体系降低维护难度。例如业务 API 与离线分析脚本解耦、分析结果通过 MySQL 回写统一提供给前端读取等，都是为了提高系统可维护性。

## 3.4 用例分析
系统主要涉及两类角色：普通用户和管理员。普通用户的主要用例包括注册、登录、查看题目、提交代码、查看提交详情、查看个人分析；管理员的主要用例包括登录、创建题目、编辑题目、管理测试用例、触发导出、查看系统统计、查看预测结果和查看题目难度分析。系统作为执行主体，还需要完成判题任务调度、日志导出、Hive 聚合和 Spark 预测。

# 第四章 系统总体设计

## 4.1 系统总体架构设计
系统采用前后端分离和单体后端相结合的总体架构。前端由 React 应用构成，负责页面交互、路由控制和数据可视化展示；后端采用 Spring Boot 单体服务，对外提供用户、题目、提交、结果、分析和预测等 REST API；MySQL 作为业务数据和分析结果数据的统一存储层；Docker 作为在线判题执行沙箱；HDFS、Hive 与 Spark 构成离线分析与预测引擎；Hadoop YARN 负责 Spark 作业资源调度。

这种架构的优点在于分工明确。在线业务请求直接访问 Spring Boot 服务，保证交互及时性；判题采用异步任务方式执行，避免长时间阻塞接口请求；分析与预测通过离线链路运行，不干扰在线事务；前端则通过统一的 API 接口从后端读取处理后的结果，避免直接依赖大数据环境。

## 4.2 系统模块划分
从功能实现角度，可以将本系统划分为以下几个核心模块。

第一，用户与权限模块。负责用户注册、登录、JWT 认证、管理员与普通用户角色区分，以及用户个人信息修改等功能。

第二，题目与测试用例模块。负责题目的创建、查询、修改以及测试用例内容录入、覆盖和删除。

第三，提交与判题模块。负责接收代码提交、创建提交记录、生成判题任务、异步拉取任务、调用 Docker 容器编译执行、输出比对以及保存判题结果。

第四，分析事件模块。负责在判题完成后记录分析事件，并支持将事件导出到 HDFS。

第五，Hive 描述性分析模块。负责按天聚合历史事件，生成全站汇总、题目维度、用户维度以及专题分析结果。

第六，Spark 预测与评估模块。负责未来提交量预测和题目难度评估，将结果写回 MySQL。

第七，前端展示模块。负责普通用户的题目访问、提交与个人分析展示，以及管理员的数据分析页、预测页和题目难度页。

## 4.3 数据库设计
系统数据库并不是只承担传统业务存储功能，而是同时承担在线业务、离线分析中间层和结果回流查询层三类职责。结合当前实现，数据库中的表可以划分为两大类：第一类是业务表，用于支撑用户、题目、提交和判题等在线流程；第二类是分析数据表，用于保存分析事件、Hive 聚合结果以及 Spark 预测和评估结果。这样的分层设计使在线事务与离线统计结果在同一数据库中完成衔接，但又通过表职责划分避免了相互混淆。

业务表中，`users` 表用于保存用户基础信息，字段包括自增主键、用户名、密码哈希和创建时间。其中用户名设置唯一约束，用于保证注册与登录时身份标识不重复；密码字段保存的是加密后的哈希值，而非明文密码。`problems` 表用于保存题目元数据，字段包括自增主键、题目标题、题目描述、时间限制、内存限制和创建时间。`testcases` 表用于保存测试用例元信息，字段包括自增主键、所属题目编号、输入文件路径、输出文件路径和权重。由于测试用例内容最终要以 `.in` 和 `.out` 文件的形式供 Docker 沙箱直接挂载使用，因此数据库只记录路径和权重，不直接存储大段测试数据内容。

`submissions` 表用于记录每次代码提交，是在线判题流程中的核心业务表。其字段包括自增主键、提交用户编号、题目编号、编程语言、源代码、提交状态、判题结果、创建时间和更新时间。其中，提交状态用于表示任务执行阶段，例如 `PENDING`、`RUNNING`、`DONE` 和 `FAILED`；判题结果用于表示该次提交的最终 verdict，例如 `PENDING`、`AC`、`WA`、`TLE`、`RE`、`CE` 和 `ERROR`。考虑到用户源代码长度不固定，系统将源代码字段设计为大文本类型，以避免较长代码被数据库截断。`judge_tasks` 表用于描述后台异步判题任务，字段包括自增主键、关联提交编号、任务状态、重试次数、创建时间、更新时间以及下次执行时间。其中，重试次数表示任务被 worker 成功领取并进入执行流程的次数；当任务执行失败但尚未超过最大重试次数时，系统会更新 `next_run_at`，使该任务在指定时间后再次进入调度范围。

`judge_results` 表用于保存每条提交最终生成的评测结果。其字段包括自增主键、关联提交编号、判题结果、运行时间、内存占用、编译错误输出、运行时错误输出、结果说明和创建时间。由于编译错误、运行错误和说明信息都可能包含较长文本或堆栈输出，因此这些字段同样采用大文本类型设计。这样一来，在线业务部分就形成了“用户—题目—测试用例—提交—任务—结果”的完整闭环，能够较好地支撑判题系统的基本功能。

分析数据表部分，最基础的一张表是 `analysis_events`。每当一次提交完成判题后，系统都会向该表写入一条事件记录。字段包括自增主键、提交编号、用户编号、题目编号、编程语言、判题结果、耗时、内存开销、事件产生时间、是否已导出到 HDFS 以及导出时间。该表一方面是导出到 HDFS 的源表，另一方面也是用户实时分析接口和部分管理员分布类接口的直接数据源。因此，`analysis_events` 在系统中承担了“在线业务到离线分析”的桥梁作用。

基于 `analysis_events` 导出到 HDFS 的历史明细数据，系统进一步通过 Hive 计算并回写多张 MySQL 结果表。基础日汇总表包括 `analysis_summary_daily`、`analysis_problem_daily` 和 `analysis_user_daily`。其中，`analysis_summary_daily` 保存某一天全站层面的基础汇总，字段包括日期、当天总提交数、当天总 AC 数、平均耗时和平均内存；`analysis_problem_daily` 保存某一天中每道题的基础聚合结果，字段包括日期、题目编号、总提交数、总 AC 数、平均耗时和平均内存；`analysis_user_daily` 保存某一天中每个用户的基础聚合结果，字段包括日期、用户编号、总提交数、总 AC 数、平均耗时和平均内存。由于这些表都是以“日期 + 维度”作为天然唯一标识，因此表结构中普遍采用组合主键设计，便于按天覆盖和按维度查询。

在基础汇总之外，系统还设计了多张专题分析结果表。`analysis_language_daily` 用于保存某一天每种语言的提交统计，字段包括日期、编程语言、提交总数、总 AC 数、平均耗时和平均内存；`analysis_verdict_daily` 用于保存某一天各种判题结果的数量分布，字段包括日期、verdict 和数量；`analysis_hourly_activity` 用于保存某一天每个小时段的提交情况，字段包括日期、小时值、提交数、AC 数和活跃用户数。除此之外，系统还设计了交叉维度结果表：`analysis_problem_verdict_daily` 保存某一天某道题在各种 verdict 下的数量；`analysis_user_language_daily` 保存某一天某个用户在不同语言上的提交统计；`analysis_user_verdict_daily` 保存某一天某个用户在不同判题结果下的数量分布。这些表本质上都是由 Hive 计算后再回写到 MySQL 的结果表，而不是直接存在于 Hive 中供前端访问。

在 Spark 模块部分，系统又额外维护了两张预测与评估结果表。`analysis_submission_forecast_daily` 用于保存未来每日提交量预测结果，字段包括自增主键、预测批次日期、目标日期、预测提交量、模型名称以及结果创建时间。该表中的 `forecast_date` 表示这批预测是哪一天跑出来的，`target_date` 表示被预测的未来日期。`analysis_problem_difficulty_daily` 用于保存题目难度评估结果，字段包括评估日期、题目编号、总提交数、总 AC 数、通过率、平均耗时、平均内存、人均尝试次数、WA 占比、RE 占比、TLE 占比、难度分数、难度标签以及模型名称。由于题目难度按“日期 + 题目”唯一确定，因此该表采用 `(dt, problem_id)` 作为组合主键，便于后续按天更新和按题回溯历史。

从数据库设计思路看，系统将在线业务表和离线分析结果表放在同一 MySQL 数据库中，并不是为了让 MySQL 直接承担所有大范围统计计算，而是为了让 MySQL 作为统一查询出口。实际的大规模日汇总、专题统计、预测和评估都依赖 HDFS、Hive 和 Spark 完成。对于需要扫描大量历史事件的统计任务，如果完全交由 MySQL 在页面访问时实时计算，不仅会增加业务数据库负担，还会使每次管理员进入分析页面时都触发重复计算，造成明显的性能浪费。基于这一考虑，系统采用“明细事件写入 MySQL—批量导出到 HDFS—Hive/Spark 离线计算—结果回写 MySQL”的链路，将重计算任务转移到大数据计算引擎中执行，而前端和后端查询接口只读取已经整理好的结果表。这样既保留了明细数据，又提高了分析结果查询效率。

## 4.4 判题流程设计
用户提交代码后，后端首先在 `submissions` 表中创建一条提交记录，并在 `judge_tasks` 表中创建对应任务。`JudgeWorker` 通过定时调度方式持续轮询待处理任务，并将任务状态从 `PENDING` 更新为 `RUNNING`。随后，`DockerJudgeRunner` 根据语言选择相应容器镜像，在容器中完成编译和运行。系统逐个读取测试用例输入文件，比较程序实际输出与标准输出，最终生成统一的 `JudgeRunResult` 对象，并将状态、耗时、内存和错误信息写入 `judge_results`。

如果判题成功结束，则提交状态更新为 `DONE`，判题结论更新为具体 verdict；如果执行过程中发生异常或超过重试次数，则任务状态会被标记为 `FAILED`。判题完成后，系统同时向 `analysis_events` 表写入一条分析事件，用于后续离线计算。

## 4.5 Docker 沙箱设计
系统为每种编程语言准备专用镜像，并在判题时通过 `docker run` 启动短生命周期容器。容器执行时采用以下安全策略：关闭网络访问、设置 CPU 和内存上限、限制进程数量、挂载只读测试数据目录、挂载可写工作目录、启用只读根文件系统以及单独的临时目录。这些策略的目标是保证容器内的用户代码无法访问外部网络、无法无限制消耗主机资源，也难以对宿主环境造成破坏。

测试数据目录采用只读挂载，避免用户代码篡改标准输入输出文件；工作目录用于保存源码文件、编译产物和程序输出文件，评测结束后及时删除；标准输出比较采用归一化策略，忽略换行风格差异和末尾空行，从而减少非本质格式问题导致的误判。

## 4.6 数据分析链路设计
系统的数据分析链路采用“在线写入、离线导出、批量聚合、结果回写”的思路。判题结束后，系统先将分析事件写入 MySQL 的 `analysis_events` 业务表。随后，管理员可以手动调用导出接口，或通过定时任务将尚未导出的事件按天写入 HDFS 对应分区目录。Hive 外表 `oj.analysis_events` 用于映射这些 HDFS 文件，进而执行基础聚合和专题分析。

聚合结果先写到 HDFS 的聚合目录，再通过脚本导入 MySQL 分析结果表。这样设计的好处在于：在线业务数据库只保存必要业务和中间日志，大规模历史统计与计算交由 Hive/Spark 完成，最终回写 MySQL 的只是较轻量的结果表，方便后端 API 快速查询。

## 4.7 预测与评估模块设计
系统当前实现了两类基于 Spark 的离线能力：其一是未来每日提交量预测，其二是题目难度评估。提交量预测使用按天聚合的历史提交数作为输入，通过简单线性回归模型估计未来七天的提交量，并将结果写入预测表；题目难度评估则根据某天各题目的 AC 率、平均尝试次数、平均耗时、运行错误比例和超时比例等指标构造难度分数，进而映射为 Easy、Medium、Hard 三个标签。

预测与评估模块都不直接服务在线事务，而是作为定期离线任务运行。这样既能利用 Spark 的批处理能力，也便于后续将模型替换为更复杂的特征工程和机器学习模型。

本章从系统整体架构、模块划分、判题流程、数据分析链路、预测模块和数据库设计六个方面给出了总体设计方案，为后续详细实现部分提供了框架基础。

# 第五章 系统详细设计与实现

## 5.1 用户与权限模块实现
用户与权限模块是系统的基础入口，其核心任务包括用户注册、登录认证、身份恢复、角色鉴权以及个人信息维护。系统在后端基于 Spring Security 构建认证框架，并结合 JWT 实现无状态会话管理。首先，在用户注册阶段，前端通过 `POST /users` 提交用户名和密码，后端会先检查用户名是否已存在。若不存在，则调用 `UserService.createUser()` 创建用户对象，并使用 `PasswordEncoder` 对原始密码进行 BCrypt 加密，最终将用户名、密码哈希值和创建时间写入 `users` 表。系统后来新增的管理员创建用户接口 `POST /admin/users` 复用了同一套创建逻辑，区别仅在于该接口需要管理员权限，而普通注册接口对外开放。

在登录阶段，系统提供 `POST /auth/login` 接口。当前端传入用户名和密码后，后端首先通过 `RateLimitService` 按客户端 IP 对登录行为进行限流，以减轻暴力尝试登录的风险。随后，系统根据用户名查询 `users` 表中的记录，并使用 BCrypt 校验密码是否匹配。

当用户名与密码校验通过后，后端调用 `JwtTokenService.generateToken()` 生成 JWT 令牌。当前实现将用户名作为 token 的核心身份标识，并根据配置项写入过期时间。前端在后续调用接口时，需要在 `Authorization` 请求头中以 `Bearer <token>` 的形式携带该令牌。系统还提供了 `GET /auth/me` 接口，用于在前端刷新页面或应用初始化时恢复当前会话。该接口会从安全上下文中读取当前用户名，再查询用户表获取用户编号与用户名，并结合当前权限判断结果返回 `ADMIN` 或 `USER` 角色标识。前端正是基于这一接口完成登录态恢复和路由权限控制。

在安全过滤链层面，系统通过 `SecurityConfig` 完成访问规则配置。当前实现关闭了默认的服务端会话状态，使用 `SessionCreationPolicy.STATELESS` 明确要求系统采用无状态认证；同时关闭 CSRF，并为本地前端开发环境配置 CORS。接口权限规则上，`/auth/login`、`POST /users` 以及健康检查接口被设置为匿名可访问；`/admin/**` 路径统一要求 `ADMIN` 角色；其余接口默认要求用户已登录。所有请求在进入业务控制器之前，都会先经过 `JwtAuthenticationFilter`。该过滤器从 `Authorization` 请求头提取 Bearer Token，调用 `JwtTokenService` 解析用户名，再通过 `UserDetailsService` 加载用户权限信息，最终将认证结果写入 `SecurityContextHolder`。后续控制器或方法级权限注解即可基于该上下文完成鉴权。

在角色模型上，本系统没有额外设计复杂的角色表，而是采用更轻量的方式：通过配置中的管理员用户名集合判断当前用户是否属于管理员。这样做虽然不适用于大型多角色业务系统，但对于教学型 OJ 平台而言，实现成本低且足够清晰。管理员权限主要用于题目管理、测试用例管理、提交记录查看、HDFS 导出、系统分析页面和预测页面访问；普通用户则只能访问自己的提交详情、个人分析页面和个人资料页面等功能。

除登录与权限判定外，系统还支持用户资料维护。普通用户可以通过 `PUT /users/me` 修改自己的用户名和密码。该接口首先会从当前安全上下文中取得用户名，确保调用方已经登录；随后，系统要求用户输入当前密码，并再次通过 BCrypt 或兼容的 SHA-256 分支进行校验，防止未验证身份就直接修改资料。若用户尝试将用户名修改为已被其他用户占用的值，系统会直接拒绝更新。只有在当前密码验证成功且新用户名合法的情况下，系统才会执行保存操作。若用户同时传入新密码，则系统会重新使用 BCrypt 加密后写回数据库；若仅修改用户名，则保留或升级原密码哈希。这样可以保证用户资料修改过程具备必要的身份确认步骤。

此外，系统还提供 `GET /users/{id}` 接口查询用户基本信息。该接口允许管理员查看任意用户信息，但普通用户只能访问与自己身份一致的记录。控制器中通过 `SecurityUtils.currentUsername()` 与目标用户的用户名进行比对，若不一致则直接返回无权限错误。这种“管理员可全量、普通用户仅限本人”的权限模型简单直观，也与平台现有功能边界保持一致。

总体来看，用户与权限模块采用“JWT 无状态认证 + 过滤器恢复身份 + 路径与方法双层鉴权 + 服务层密码校验”的实现方式，既满足了本系统对登录、鉴权和资料维护的基本需求，又兼顾了前后端分离应用对会话恢复与权限控制的实际要求。

## 5.2 题目与测试用例模块实现
题目与测试用例模块负责维护平台中的题目元数据和判题所需的标准测试数据，是在线判题系统中最核心的业务模块之一。当前系统中的题目基础信息包括题目标题、题目描述、时间限制和内存限制，这些字段统一存储在 `problems` 表中。后端通过 `ProblemController` 暴露题目相关接口，普通用户和管理员共同使用同一个题目领域模型，但在返回内容和可执行操作上存在明显差异。

在题目列表查询阶段，系统提供 `GET /problems` 接口。该接口首先按题目编号升序查询全部题目记录，然后进一步调用 `ProblemService.findLatestDifficultyLabels()`，从题目难度分析结果表中批量读取每道题最新日期对应的难度标签，并将该标签一并组装到题目列表响应中。若某道题尚未参与过难度评估，或者分析结果表中还没有它的记录，则后端会在响应中为其填充“暂无分类”。这种设计避免了前端自行拼接分析结果，也使题目列表能够直接展示当前最新的难度评估结论。

在题目创建阶段，管理员通过 `POST /problems` 接口提交题目元数据。当前实现中，创建请求不仅可以包含标题、描述、时间限制和内存限制，还可以在同一请求中附带初始化测试用例。系统在 `ProblemService.createProblem()` 中会先保存题目本身，获取其主键后，再根据请求内容决定如何处理测试用例。若请求中传入的是路径式测试用例列表，则系统直接将输入文件路径、输出文件路径和权重写入 `testcases` 表；若请求中传入的是测试用例内容，则系统会进一步调用测试用例存储服务，将输入内容和标准输出内容写成本地文件后，再把生成的文件路径及权重保存到数据库。这种设计兼顾了两种录题方式：既支持已有测试文件的快速登记，也支持通过后台页面直接录入测试数据内容。

测试用例内容式管理是本系统题目模块的重要实现特点。管理员在页面上输入 `inputContent` 和 `outputContent` 后，后端并不会简单把这两段文本直接存入数据库，而是通过 `TestcaseStorageService` 将其写入本地测试数据目录，并为当前题目生成对应的 `.in` 和 `.out` 文件。数据库中的 `testcases` 表只保存测试用例所属题目编号、输入文件路径、输出文件路径和权重等元信息，而不直接存放大段测试内容。这样设计有两个明显优点：其一，测试数据文件能直接被 Docker 判题流程挂载使用，无需再从数据库中恢复到文件系统；其二，数据库结构保持轻量，更适合作为索引和元数据存储层。

在题目详情查询阶段，系统提供 `GET /problems/{id}` 接口。该接口首先根据题目编号查询 `problems` 表中的记录，再按身份决定是否返回测试用例列表。若当前访问者为管理员，则系统会额外查询该题的全部测试用例，并将每个测试点的路径信息与权重封装到响应中；若访问者为普通用户，则后端返回的题目详情中测试用例列表为空。这样做的目的在于防止标准输入输出路径和测试数据结构泄露给普通用户，从而保证判题公平性。管理员则需要完整测试用例信息来完成维护工作，因此保留可见性是合理的。

题目元数据更新由 `PUT /problems/{id}` 接口完成，且仅允许管理员访问。更新逻辑相对直接：后端根据题目编号查出对应实体，覆盖其标题、描述、时间限制和内存限制后保存回数据库。由于题目元数据和测试用例属于相对独立的两类信息，因此当前系统没有将测试用例修改逻辑混入题目元数据更新接口，而是为测试用例单独提供了增删改查接口。这种拆分方式使接口职责更加单一，前端管理页面的交互结构也更清晰。

在测试用例维护方面，系统提供了独立的新增、查看、覆盖和删除接口。管理员可通过 `POST /problems/{id}/testcases` 新增测试用例内容，后端会校验题目是否存在，再将输入输出内容写入文件并在 `testcases` 表中创建记录；可通过 `GET /problems/{id}/testcases` 查看该题所有测试点；可通过 `PUT /problems/{problemId}/testcases/{testcaseId}` 对指定测试用例进行覆盖写入，系统会保留原文件路径，仅将输入输出文件内容重写，并按需更新权重；还可以通过 `DELETE /problems/{problemId}/testcases/{testcaseId}` 删除测试用例，系统在删除数据库记录前会先删除对应的 `.in` 和 `.out` 文件，避免测试数据目录中残留无用文件。由此可见，本系统中的测试用例管理不是单纯的数据库记录维护，而是数据库元信息与本地文件系统内容的联动管理。

为了保证接口行为符合角色边界，题目模块中的创建题目、修改题目、增删改测试用例等接口均通过 `@PreAuthorize("hasRole('ADMIN')")` 进行方法级限制，而题目列表和普通详情查询则对所有已登录用户开放。普通用户能够看到题目标题、描述、时间限制、内存限制以及最新难度分类，但看不到任何测试数据内容；管理员则在此基础上拥有完整的录题与维护能力。这种分层返回策略既满足了普通用户做题所需的信息最小集，也避免了因接口设计不当导致测试数据泄露。

总体而言，题目与测试用例模块采用“题目元数据入库 + 测试数据文件化存储 + 数据库记录路径索引 + 角色差异化返回”的实现方式，使题目录入、题目展示、测试用例维护和判题数据准备形成了闭环。该模块不仅服务于基础做题流程，也为后续 Docker 判题、题目难度评估以及前端题目列表中的难度展示提供了直接支撑。

## 5.3 提交与判题模块实现
当用户在题目页面点击 `Submit` 按钮后，前端会调用代码提交接口，后端首先对提交内容进行基本校验，例如题目是否存在、当前用户是否已登录、提交频率是否超限以及源码大小是否超过系统限制。校验通过后，后端并不会立即进行判题，而是先将本次提交写入 `submissions` 表，并同时在 `judge_tasks` 表中创建一条待执行的判题任务。也就是说，在这一阶段系统只是完成了“提交入队”，尚未真正执行编译与运行。

本系统采用的是异步判题模型。后台的 `JudgeWorker` 组件会按照固定时间间隔轮询 `judge_tasks` 表，检查当前是否存在状态为 `PENDING` 的任务。为了避免同时执行过多判题任务导致宿主机资源竞争，系统使用 `Semaphore` 对并发数量进行控制，并结合线程池将可执行任务异步分发出去。当某个待判题任务被成功抢占后，其状态会从 `PENDING` 更新为 `RUNNING`，随后由线程池执行实际判题流程。需要说明的是，`JudgeWorker` 并不是直接调用 Docker 判题，而是先调用 `JudgeService`，再由 `JudgeService` 统一协调 `DockerJudgeRunner` 执行具体编译和运行逻辑。这样的分层设计使任务调度、业务状态更新和容器执行逻辑彼此解耦，便于维护和扩展。

在具体判题执行过程中，`DockerJudgeRunner` 会首先根据本次提交创建一个临时工作目录。该目录位于系统配置的工作目录之下，通常命名为 `sub-{id}`，其中 `id` 为本次提交的编号。随后，系统根据用户选择的编程语言，在该临时目录中写入对应的源代码文件。例如，若用户选择 Java，则会生成 `Main.java`；若选择 C++，则会生成 `Main.cpp`。在源码写入后，系统根据语言类型生成相应的编译与运行配置，包括源文件名、编译命令和运行命令，并选择与该语言对应的 Docker 镜像。

在构建 Docker 判题沙箱时，系统首先设置一系列安全策略。其一，使用 `--network none` 彻底关闭容器网络访问，防止用户代码访问外部网络；其二，使用 `--security-opt no-new-privileges` 禁止进程通过漏洞或特殊机制进行权限提升；其三，使用 `--cap-drop ALL` 丢弃容器进程的全部 Linux capability，避免容器具备修改系统资源或执行高危操作的能力；其四，使用 `--read-only` 将容器根文件系统设置为只读，防止容器进程在系统目录中任意写入内容。通过这些措施，可以显著降低恶意代码或异常程序对宿主机环境的潜在影响。

在资源隔离方面，系统通过 `--cpus`、`--memory` 和 `--pids-limit` 对容器可使用的 CPU、内存和进程数进行限制。例如，系统可将容器 CPU 限制为 1 核、内存限制为 256MB，同时限制容器内最多只能创建有限数量的进程。这样做的目的在于防止用户代码通过死循环、递归爆栈、大量创建子进程等方式过度消耗宿主机资源，影响系统稳定性。

考虑到编译器、解释器或运行时环境通常需要在临时目录中写入缓存文件和中间文件，系统还单独使用 `--tmpfs /tmp:rw,nosuid,nodev,noexec,size=64m` 和 `--tmpfs /var/tmp:rw,nosuid,nodev,noexec,size=64m` 为容器提供基于内存的临时文件系统。其中，`rw` 表示允许读写，`nosuid` 表示禁止通过 setuid/setgid 文件提权，`nodev` 表示不允许解释设备文件，`noexec` 表示不允许直接执行该目录中的文件，`size=64m` 则限制临时目录最大容量。这样既保留了编译和运行所需的临时写入能力，又避免临时目录成为执行恶意代码和无限制消耗资源的入口。

在容器目录映射方面，系统会将宿主机上的临时工作目录挂载到容器内部的 `/workspace`，并将 `/workspace` 设置为容器的工作目录。对于运行阶段，还会将宿主机上的测试数据目录挂载到容器内部的 `/testcases`，并额外加上 `:ro` 参数，将该目录设为只读，防止用户代码篡改测试输入和标准输出文件。最终，系统通过 `/bin/sh -c command` 的形式在容器内执行编译命令或运行命令。

对于需要编译的语言，容器在编译成功后会在临时工作目录中生成对应的编译产物。例如，C 与 C++ 的编译命令会显式指定输出文件为 `/workspace/a.out`，因此在宿主机对应的工作目录中可以看到 `a.out` 可执行文件；Java 则会在工作目录下生成 `Main.class` 字节码文件；Python 由于属于解释执行语言，因此没有独立的编译产物文件。需要指出的是，这些文件都只是判题过程中的临时文件，在本次提交流程结束后会被系统统一清理。

完成编译后，`DockerJudgeRunner` 会循环处理当前题目的每一个测试用例。每个测试用例都包含一个输入文件和一个期望输出文件，通常分别以 `.in` 和 `.out` 为后缀，保存在宿主机测试数据目录中。运行阶段，系统根据语言类型生成相应的运行命令，并将测试输入文件重定向给待执行程序，同时将程序标准输出重定向到工作目录下的 `out.txt`。例如，对于 C++ 程序，运行命令实质上是执行前面编译得到的 `a.out`，并将测试输入文件内容作为标准输入传入程序。运行阶段的 Docker 调用除了前述的安全和资源限制外，还会使用 `/usr/bin/time -f "TIME:%e MEM:%M"` 对执行时间和内存进行测量，并将这些统计信息写入标准错误输出，供系统后续解析。

当 Docker 执行完运行命令后，工作目录中会生成一个实际输出文件 `out.txt`。随后系统会依次进行判题结果判定。首先，系统会解析 `/usr/bin/time` 输出的时间和内存信息，用于形成更准确的性能统计结果。对于时间限制判定，当前实现并不是简单比较统计出的总时间是否大于题目限制，而是为每个测试点单独设置一个超时时间窗口。如果外部进程没有在该超时时间内完成，`ProcessRunner` 会强制终止进程，此时系统直接判定该测试点为 `TLE`。如果进程在规定时间内结束，但返回的退出码不为零，则说明程序在运行中出现异常，系统判定为 `RE`。如果程序执行结束后未能生成 `out.txt`，也判定为 `RE`。若 `out.txt` 存在，但输出文件大小超过系统设定上限，则判定为输出超限场景并按运行异常处理。若输出文件与标准答案文件内容不一致，则判定为 `WA`。只有在程序在所有测试点上均顺利完成、输出合法且与标准答案一致时，系统才会最终返回 `AC`。

整个判题过程结束后，系统会将判题结果写入 `judge_results` 表，并将 `submissions` 表中的状态更新为 `DONE`，将具体 verdict 一并写回。同时，系统会清理该提交对应的临时工作目录，删除源码文件、编译产物和输出文件，以释放磁盘空间并降低安全风险。

## 5.4 判题稳定性与安全机制实现
为提高判题稳定性，系统实现了任务重试、工作目录清理和并发控制等机制。对于执行过程中出现的异常，worker 会记录重试次数，并在达到上限后将任务标记为失败；每次判题完成后，系统会删除工作目录中的源码、编译产物和输出文件，避免磁盘堆积；并发控制则通过固定数量的执行线程和资源限制实现，以防止短时间内大量任务同时触发容器竞争。

在安全方面，除 Docker 容器隔离外，系统还实现了提交限流、防止过大代码与异常输出占用空间等措施。虽然这些机制不能覆盖所有安全场景，但对于教学训练环境已具备较好的防护能力。

## 5.5 分析事件导出与 Hive 聚合实现
为了支撑后续的大数据分析与预测任务，系统在每次判题完成后，都会将该次提交对应的关键分析信息写入 MySQL 中的 `analysis_events` 表。该表记录了提交编号、用户编号、题目编号、编程语言、判题结果、运行时间、内存占用以及提交时间等字段，是后续 Hive 聚合和 Spark 预测的原始数据来源。通过将业务执行结果结构化为分析事件，系统实现了在线业务与离线分析之间的桥接。

系统通过管理员接口 `/admin/export-hdfs` 将 `analysis_events` 中尚未导出的数据批量写入 HDFS。导出流程可以概括为以下几个步骤。第一步，系统从 `analysis_events` 表中查询所有尚未导出的记录，并按照配置的批大小限制本次导出数量。若本批次没有可导出的记录，则接口直接返回 0。第二步，系统根据配置确定 HDFS 的 URI 和分析数据目录，例如 `/oj/analysis`，并按照当天日期生成分区目录 `dt=YYYY-MM-DD`。同时，为了保证文件名唯一，系统使用当前时间戳拼接生成以 `events-` 开头、以 `.csv` 结尾的文件名。第三步，系统通过 Hadoop 的 `FileSystem` API 连接 HDFS，创建分区目录和目标 CSV 文件，并先写入一行表头，随后逐条写入本次待导出的分析事件数据。第四步，HDFS 文件写入完成后，系统将本批次事件标记为已导出，并记录导出时间，最后接口返回实际导出的事件条数。

由于导出的文件是标准 CSV 格式，且文件第一行包含列名，因此在 Hive 建立外表时，系统通过 `skip.header.line.count=1` 的表属性显式指定跳过表头行，避免 Hive 将表头误解析为数据内容。该设计在实际运行中十分重要，因为若不跳过表头，Hive 和 Spark 在读取外表时可能会将字符串型表头解析为数值型字段的空值，进而影响后续聚合与预测结果。

为了完成离线统计，系统编写了专门的 Hive SQL 脚本。该脚本首先创建数据库 `oj`，再创建外部表 `oj.analysis_events`，并将 HDFS 中的 `/oj/analysis` 目录设置为表的存储位置。随后，通过 `MSCK REPAIR TABLE` 刷新分区信息，使 Hive 能识别新增的按日期分区目录。在聚合阶段，每一条 Hive SQL 语句都以传入的日期参数作为筛选条件，即只对某一天的分析事件进行统计，并将结果通过 `INSERT OVERWRITE DIRECTORY` 写入 HDFS 中对应的聚合结果目录，而不是直接写到虚拟机本地文件系统。例如，基础聚合结果会写入 `/oj/analysis_agg` 目录下的不同子目录，专题分析结果则写入 `/oj/analysis_desc` 目录下的不同子目录。

这些 HDFS 聚合结果往往由多个 part 文件组成，不便于直接导入 MySQL。因此，系统还编写了相应的 shell 脚本，在脚本中先使用 `hdfs dfs -getmerge` 将某一天对应目录下的多个结果文件合并到虚拟机本地的临时目录，生成单个 CSV 文件；随后，再使用 `LOAD DATA LOCAL INFILE` 将该本地 CSV 文件导入 MySQL 的分析结果表中。通过这种“Hive 写 HDFS—脚本合并到本地—MySQL 导入”的方式，系统实现了从大数据离线计算结果到业务数据库查询表的转换。

为了支持不同层级和不同维度的分析需求，系统设计并维护了多张分析结果表。其中，`analysis_summary_daily` 保存某一天全站层面的基础汇总信息，例如总提交量、总通过数、平均时间和平均内存；`analysis_problem_daily` 保存某一天每道题的基础聚合结果；`analysis_user_daily` 保存某一天每个用户的基础聚合结果。这三张表构成了系统最基础的日报统计体系。

在此基础上，系统又构建了多张专题分析表。`analysis_language_daily` 用于保存某一天每种语言的提交数量、通过数量以及平均性能指标；`analysis_verdict_daily` 用于保存某一天各种 verdict 的数量分布；`analysis_hourly_activity` 用于保存某一天每个小时段的提交总量、通过总量和活跃用户数；`analysis_problem_verdict_daily` 用于保存某一天某道题下各种 verdict 的数量；`analysis_user_language_daily` 用于保存某一天某个用户在不同语言上的提交统计；`analysis_user_verdict_daily` 用于保存某一天某个用户各种 verdict 的数量分布。这些表共同构成了系统前端分析页面的数据支撑层。

通过上述设计，系统实现了从 `analysis_events` 明细日志到 Hive 批量聚合，再到 MySQL 结果表回流的完整分析链路。这种设计一方面保留了历史原始日志，适合长期扩展分析；另一方面也使前端页面只需要读取 MySQL 中结构清晰的结果表，无需直接访问 Hive 或 HDFS，从而降低了在线访问的复杂度。

## 5.6 Spark 提交量预测实现
在完成 Hive 基础聚合和描述性分析之后，系统进一步引入 Spark 对历史提交数据进行预测，以增强平台对未来运行趋势的感知能力。当前实现的第一个预测模块是“每日提交量预测”，其目标是在已有历史数据基础上，对未来 7 天的全站提交量进行估计，并将预测结果写回 MySQL，供管理员页面直接展示。

该模块首先通过 Spark SQL 直接查询 Hive 数据仓库中的基础事件表 `oj.analysis_events`。查询逻辑以日期字段 `dt` 为分组依据，对全站每日提交数进行聚合，并按日期顺序进行排序，从而得到一个按时间排列的历史提交量序列。由于线性回归模型至少需要两个样本点才能进行拟合，因此系统在取回历史聚合结果后，会进行数据量校验：若历史可用数据少于两天，则直接抛出 `RuntimeError` 并中止后续流程，以避免在冷启动或数据不足情况下产生无意义预测结果。

由于机器学习模型不能直接理解形如 `2026-04-08` 这样的日期字符串，系统在特征构造阶段对时间序列进行了数值化处理。具体做法是：按日期顺序遍历历史数据，为每一天分配一个从 0 开始递增的索引 `day_index`，将其作为模型的自变量，而每日总提交量 `total_submissions` 作为因变量。随后，系统使用 Spark MLlib 中的 `VectorAssembler` 组件，将 `day_index` 封装成模型训练所需的特征向量 `features`，从而完成从关系型统计结果到机器学习输入格式的转换。

在模型训练阶段，系统实例化了一个线性回归模型 `LinearRegression`，并显式指定 `features` 列作为输入特征，`label` 列作为目标值，预测结果写入 `prediction` 列。随后调用 `fit()` 方法在 Spark DataFrame 上完成模型训练。该过程的本质是由 Spark MLlib 根据历史数据拟合出时间序列与提交量之间的线性关系，从而形成一个可以用于未来日期推断的预测模型。

训练完成后，系统开始构造未来 7 天的预测输入集。首先，系统读取历史数据中最后一天的日期，并将其转换为标准日期对象；其次，以该日期为基准，利用 `timedelta` 逐日推算未来 1 到 7 天的目标日期；再次，沿用历史数据的总天数作为起始索引，继续为未来 7 天分配递增的 `day_index`。这样便得到了未来 7 天的特征向量集合。系统再将该集合输入前面训练得到的线性回归模型，并调用 `transform()` 方法生成未来 7 天的预测提交量。

预测结果生成后，系统并不会直接写库，而是会先执行一系列业务化处理。首先，为每条预测记录附加当前的预测批次日期 `forecast_date` 和模型名称 `model_name`，以便后续追踪某一天生成的预测结果来自哪个模型版本。其次，由于线性回归在某些情况下可能产生负数预测值，而实际业务中“每日提交量”必然是非负整数，因此系统会对预测结果进行二次清洗：将预测值转换为整型，并将空值或负值统一修正为 0，从而保证输出结果符合业务常识。

在结果持久化方面，系统采用了幂等性设计。具体而言，在将预测结果写入 MySQL 的 `analysis_submission_forecast_daily` 表之前，系统会先通过 JDBC 连接执行一条删除语句，清除同一 `forecast_date` 且同一 `model_name` 下的历史记录；随后，再将本次新生成的预测结果以追加方式写入数据库。这种“先删除、再插入”的方式可以保证即使同一天内重复执行该预测脚本，也不会在结果表中产生重复数据，从而确保前端页面和后续分析读取到的始终是当前批次的唯一结果。最后，系统在任务结束时关闭 SparkSession，释放 YARN 集群中的计算资源。

从实现效果看，该模块虽然采用的是较为基础的线性回归方法，但已经成功打通了“Spark 读取 Hive—构造模型输入—执行预测—清洗结果—幂等写回 MySQL”的完整链路，为后续引入更复杂的预测模型奠定了基础。

## 5.7 Spark 题目难度评估实现
除了对平台整体提交量进行预测之外，本文还进一步利用 Spark 实现了题目难度评估模块。与提交量预测不同，该模块的目标并不是预测未来数值，而是基于历史判题行为对某一天各道题目的综合难度进行量化评估，并自动生成难度标签，用于支撑管理员的题库管理和教学分析。

该模块首先根据传入的日期参数，从 Hive 外表 `oj.analysis_events` 中筛选出指定日期的全部评测记录。随后，Spark 按题目编号 `problem_id` 进行分组聚合，统计每道题在当天的总提交次数、通过次数、独立活跃用户数、平均运行时间、平均内存占用，以及 `WA`、`RE`、`TLE` 等 verdict 的数量。通过这一过程，系统获得了每道题的基础事实数据。

在此基础上，系统进一步推导出多项能够反映题目挑战程度的比率型指标。首先，根据通过次数与总提交次数计算题目的通过率 `AC Rate`；其次，通过总提交次数除以独立活跃用户数，得到人均尝试次数 `Attempts per user`，用于反映学生平均需要尝试多少次才能完成该题；再次，将 `WA`、`RE`、`TLE` 的数量分别除以总提交次数，得到错误类型比例。这样，系统就从原始提交日志中提取出了一组更适合用于难度分析的结构化特征。

为了使不同量纲的指标能够进行统一加权，系统在后续处理中引入了归一化和边界限制机制。首先，系统自定义了 `clamp01` 函数，确保参与最终计算的得分因子被严格限制在 0 到 1 之间，避免异常值放大影响。其次，系统利用 Spark 的窗口函数 `Window.partitionBy()` 计算当天所有题目中最大的平均运行时间和最大的人均尝试次数，并以它们为分母，将各题目的绝对值转化为相对的 `time_score` 和 `attempt_score`。通过这种全局归一化方式，系统能够在同一天的题目集合中衡量“某道题的运行时间或尝试次数在整体中的相对水平”。

在难度分数计算阶段，系统采用如下加权公式：

$$
\text{difficulty\_score} = 0.45 \times (1 - \text{AC Rate}) + 0.20 \times \text{Attempt Score} + 0.15 \times \text{Time Score} + 0.10 \times \text{RE Rate} + 0.10 \times \text{TLE Rate}
$$

从该公式可以看出，题目通过率是权重最高的因素，因为通过率最能直接反映题目的总体难度；人均尝试次数和平均运行时间用于反映题目在求解过程中的尝试成本与性能压力；运行错误比例和超时比例则反映题目实现过程中对程序健壮性和复杂度控制的挑战。需要指出的是，这一模块属于规则型难度评估，而不是监督学习分类模型。系统并未使用人工标注的难度标签训练分类器，而是通过多指标加权方式生成一个可解释的综合难度分数。

在得到 `difficulty_score` 后，系统进一步进行标签映射：若分数小于 0.35，则将题目判定为 `Easy`；若分数位于 0.35 到 0.65 之间，则判定为 `Medium`；其余情况判定为 `Hard`。通过这一规则，系统能够将连续型难度分数转化为更适合展示和理解的离散型难度标签。这样一来，管理员不仅能看到题目之间的相对难度差异，还能够从宏观上掌握题库难度结构是否均衡。

在结果持久化阶段，系统与提交量预测模块一样采用幂等性写入策略。具体而言，在写入 MySQL 的 `analysis_problem_difficulty_daily` 表之前，脚本会先删除指定日期下已有的旧记录，再通过 JDBC 追加写入本次重新计算得到的结果。这样可以保证同一天的难度评估结果在多次运行脚本时始终保持唯一和一致，避免重复数据影响后端页面查询和前端展示。

总体来看，题目难度评估模块实现了从分析事件日志到题目质量度量的转换过程。它将原本分散在用户提交中的通过率、错误率和性能表现重新组织为可解释的难度指标，使系统具备了题库质量评估和难度标签生成能力。这不仅增强了在线判题系统的数据分析深度，也为后续进一步引入更复杂的题目画像、难度预测和推荐机制打下了基础。

## 5.8 前端可视化页面实现
前端部分采用 `React + Vite + TypeScript` 实现，整体结构按照“路由层—布局层—页面层—数据访问层”进行划分。路由入口定义在 `router.tsx` 中，系统首先区分访客路由、普通登录路由和管理员路由。`/login` 与 `/register` 由 `GuestRoute` 包裹，仅允许未登录用户访问；其余业务页面统一挂载在 `AppLayout` 之下，并由 `ProtectedRoute` 要求用户必须已经登录；管理员专属页面如 `/admin/problems`、`/admin/analytics`、`/admin/perdict`、`/admin/problems/difficulty` 和 `/admin/submissions` 等，则进一步通过 `AdminRoute` 进行角色校验。这样的实现使前端在路由层就完成了角色边界划分，避免未授权用户进入后台管理页面。

为了恢复前端会话状态，系统在 `useAuth` 中维护当前用户信息、JWT 令牌和管理员标记。用户登录成功后，前端将 token 写入 `localStorage`；当页面刷新或应用重新加载时，前端会先读取本地 token，再调用后端 `GET /auth/me` 接口恢复当前登录用户的编号、用户名和角色信息。若恢复失败，则前端会主动清理本地 token 并跳回登录页面。这种实现方式与后端的 JWT 无状态认证机制相匹配，使前端无需依赖服务端 session 即可维持登录态。

在页面公共布局上，系统采用 Ant Design 的 `Layout` 组件构建统一后台壳。左侧导航栏由 `AppLayout` 根据当前用户是否为管理员动态生成菜单项。普通用户只看到题目列表、个人分析页和个人资料页；管理员则在此基础上额外看到题目管理、创建题目、创建用户、提交记录、题目难度分析、系统分析、预测页面和 HDFS 导出等菜单项。顶部 Header 区域统一显示当前用户名与角色，并提供退出登录按钮。这样既减少了重复页面结构代码，也保证了不同页面之间的导航方式一致。

在数据访问层，前端统一通过封装过的 Axios 实例发送请求。该实例在请求拦截器中自动附加 `Authorization: Bearer <token>` 请求头，并在响应拦截器中集中处理 `401` 和 `403` 等错误：当后端返回 `401` 时，前端自动清除登录状态并跳转到登录页；当返回 `403` 时，则通过页面消息组件提示用户权限不足。这样可以避免在每个页面重复编写认证和异常处理逻辑。对于页面中的服务端状态管理，系统采用 React Query。在具体页面中，列表查询、统计图表和详情数据均通过 `useQuery` 发起请求，并根据 query key 自动完成缓存、重取和加载状态管理，从而降低了页面状态控制复杂度。

题目相关页面主要包括 `/problems` 和 `/problems/{id}`。题目列表页通过调用 `GET /problems` 获取所有题目数据，在表格中展示题目编号、标题、难度标签、时间限制和内存限制等信息。其中难度列直接使用后端返回的最新难度分类结果，并通过 `Tag` 组件以不同颜色展示 `Easy`、`Medium`、`Hard` 或“暂无分类”。题目详情页则调用 `GET /problems/{id}` 获取单题信息，并提供代码提交入口。根据系统后端的权限设计，普通用户在该页面只能看到题目标题、描述和资源限制，而不会看到测试用例内容。提交结果页 `/submissions/{id}` 则负责展示单次提交的状态、判题结果、时间和内存等信息。

管理员侧题目管理页面包括 `/admin/problems`、`/admin/problems/create` 和 `/admin/problems/{id}`。题目列表页提供题目查看与管理入口；创建页通过表单录入题目标题、描述、时间限制和内存限制，并支持直接填写初始化测试用例内容；管理页则同时承担题目元数据编辑和测试用例管理功能。测试用例的新增、覆盖和删除操作分别调用后端 `POST /problems/{id}/testcases`、`PUT /problems/{problemId}/testcases/{testcaseId}` 和 `DELETE /problems/{problemId}/testcases/{testcaseId}` 接口，前端在页面中将测试点内容表单与测试用例列表组合展示，使管理员能够在同一路由下完成完整维护流程。

除题目管理外，系统还为管理员实现了“创建用户”和“提交记录查看”两个后台页面。`/admin/users/create` 页面通过简单表单调用 `POST /admin/users` 接口，为平台直接创建普通用户。`/admin/submissions` 页面则调用管理员提交记录接口，按提交时间升序展示所有提交的用户名、题目标题、verdict 和创建时间，并在每行提供 `View` 按钮。点击按钮后，页面使用 Drawer 弹层调用提交详情接口，展示该条提交的语言、状态、verdict、时间、内存、编译错误、运行错误以及完整源代码。由于详情展示采用 Drawer 而不是新路由，因此管理员可以在不离开列表页面的情况下快速查看多条提交记录。

普通用户分析页面 `/analytics/user` 是前端数据可视化的重要入口。该页面分别调用 `GET /analytics/user/overview`、`GET /analytics/user/daily`、`GET /analytics/user/language`、`GET /analytics/user/verdict`、`GET /analytics/user/language/daily`、`GET /analytics/user/verdict/daily`、`GET /analytics/user/problems` 和 `GET /analytics/user/recent` 等接口，并使用 Ant Design 的统计卡片、表格组件与 ECharts 图表组合展示结果。页面上方通过 `Statistic` 组件显示总提交数、通过数、通过率、平均时间和平均内存；中间部分分别使用折线图、柱状图和饼图展示 30 天提交趋势、30 天 AC Rate、语言分布、verdict 分布、每日语言活动和每日 verdict 活动；下方再通过表格展示题目统计和最近提交记录。每个图表在后端无数据时都会展示统一的空态组件，避免页面空白。

管理员系统分析页面 `/admin/analytics` 则面向平台整体运行情况。该页面通过日期选择器和时间范围选择器控制查询条件，并分别调用管理员总览、趋势、语言分布、verdict 分布、小时活跃度、热门题目、热门用户和单题 verdict 细分等接口。前端在页面顶部显示当天全站提交数、通过数、通过率、平均时间、平均内存和活跃用户数；中间区域使用组合图展示近 N 天趋势、近 N 天 AC Rate、多日语言趋势、多日 verdict 趋势、某天小时活跃度以及热门题 verdict 细分；页面底部则通过两个表格展示当天 Top Problems 和 Top Users。由于这些数据全部来自 MySQL 中的离线聚合结果表，因此前端无需直接访问 Hive 或 Spark，只需要面向 REST API 完成展示即可。

在预测与评估类页面中，系统分别实现了 `/admin/perdict` 和 `/admin/problems/difficulty` 两个独立路由。预测页面通过 `GET /analytics/admin/forecast/submissions` 接口获取某一预测批次的未来提交量数据，并展示预测批次日期、预测天数、总预测量、平均预测量、峰值预测量、未来提交量折线图以及预测明细表。题目难度评估页面则通过 `GET /analytics/admin/problems/difficulty` 和 `GET /analytics/admin/problems/{id}/difficulty/history` 接口获取题目难度标签分布、最难题排行、单题难度历史和题目难度明细表。页面中提供日期选择、难度标签筛选以及题目选择下拉框，方便管理员在同一页面中切换不同分析条件。这样，Spark 生成的预测与评估结果就被前端直接转化为了可查询、可筛选、可比较的页面内容。

在图表渲染方式上，系统统一采用 `echarts-for-react` 作为 ECharts 的 React 封装，并根据不同数据形态选择合适的图表类型：趋势型数据使用折线图或柱线组合图，结构占比数据使用环形饼图，多类别随时间变化数据使用堆叠柱状图或多折线图，题目明细和提交明细则使用表格展示。这样一方面保持了页面风格统一，另一方面也使用户能够快速根据图表形式理解当前信息所表达的业务含义。

总体来看，前端页面实现并不是简单地将接口数据直接罗列出来，而是围绕“登录态恢复、路由权限控制、统一布局、统一请求封装、图表与表格混合展示”这一思路进行组织。通过这些实现，系统最终形成了从后端 REST API 到前端交互页面的完整产品化闭环，使判题结果、离线统计、Spark 预测和难度评估都能够以统一、可操作的方式呈现给普通用户和管理员。

## 5.9 本章小结
本章围绕系统的关键模块实现展开，详细说明了用户权限管理、题目与测试用例管理、异步判题执行、Docker 安全沙箱、分析事件导出、Hive 描述性分析、Spark 提交量预测、Spark 题目难度评估以及前端页面实现过程，体现了系统从业务执行到数据分析再到预测展示的完整实现路径。

## 6.1 可视化模块设计目标

本文所实现的在线判题系统不仅需要完成代码提交、自动判题和结果返回等基础功能，还需要进一步将系统在运行过程中积累的数据转化为可被用户和管理员直接理解的信息。仅仅完成 Hive 与 Spark 的离线计算并不能充分体现大数据计算引擎在系统中的实际价值，只有将分析结果以图表、表格和指标卡片等方式进行可视化展示，才能真正形成“数据沉淀—离线计算—结果回流—页面应用”的完整闭环。因此，在系统设计中，前端分析页面并不是附属模块，而是系统数据价值落地的重要组成部分。

本系统中的可视化模块主要服务于两类对象：一类是普通用户，另一类是管理员。普通用户更加关注自身的做题状态、学习节奏和常见错误，因而页面重点是个人提交趋势、个人语言偏好、个人判题结果分布以及对已做题目的掌握情况；管理员则更关心平台整体运行状态、学生群体提交行为、题目质量与资源负载情况，因此页面重点是全站趋势、语言分布、结果分布、活跃时段、热门题目以及活跃用户。通过这种分角色设计，系统能够在同一套数据基础上，分别支撑学生自我反馈与平台管理决策。

从设计原则上看，本系统的可视化模块遵循以下三个目标。第一，展示内容要尽量与业务场景直接对应，避免出现虽然计算复杂但难以解释的图表。第二，图表之间要形成互补关系，例如既有单日分布图，也有多日趋势图，从而兼顾静态观察与动态观察。第三，页面中的图表应具有明确用途，不只是“展示数据”，还应能够帮助用户或管理员得出实际判断，例如是否出现学习懈怠、某类错误是否明显增多、某一时段是否存在系统负载高峰等。

在本章中，主要围绕两个核心分析页面展开：管理员侧的 `System Analytics` 页面和普通用户侧的 `My Analytics` 页面。由于论文篇幅和展示重点的限制，没有必要将页面中的所有图表逐一截图展示，因此更合理的写法是选择能够代表“趋势、分布、时段、结构和个体反馈”这几个核心维度的图表作为插图对象，而其他图表则通过正文进行说明与归纳分析。

## 6.2 管理员系统分析页面设计与应用价值

### 6.2.1 页面总体设计

管理员侧的 `System Analytics` 页面承担的是平台级观察与管理决策支撑功能。与普通用户页面不同，管理员页面不再聚焦单个用户的学习行为，而是从全局视角分析平台在某一时间段内的整体运行情况，包括提交规模、通过情况、语言使用结构、判题结果结构、活跃时段分布、热门题目和活跃用户等。该页面的设计目标，是让管理员能够在较短时间内把握平台运行状态，并根据分析结果进一步判断是否需要调整教学安排、优化题目内容或者对系统资源进行预留。

从页面结构上看，管理员分析页面由三层组成。第一层是顶部的概览指标，用于快速反映当天全站关键状态；第二层是趋势图和分布图，用于从时间与结构维度观察平台数据变化；第三层是热门题目、活跃用户和题目结果细分等明细型展示，用于帮助管理员进一步定位问题来源。这样的组织方式符合管理类页面“先总览、后分析、再定位”的阅读逻辑。

### 6.2.2 顶部概览指标的用途与意义

管理员页面顶部通常展示 `Daily Submissions`、`Daily Accepted`、`Daily AC Rate`、`Average Time`、`Average Memory` 和 `Active Users` 等指标。这些指标虽然不是复杂图表，但在管理页面中具有非常重要的作用。`Daily Submissions` 和 `Daily Accepted` 用于反映当天平台整体提交规模与通过数量，是最直接的活跃度指标；`Daily AC Rate` 则能够从整体上反映当天题目完成情况，帮助管理员快速判断学生整体做题状态是否正常；`Average Time` 和 `Average Memory` 能够从运行层面反映当天代码执行表现；`Active Users` 则从参与人数维度反映平台实际使用情况。

这些指标的意义在于，它们为管理员提供了一个“第一眼判断”。如果某天 `Daily Submissions` 显著降低，那么可能意味着学生使用频率下降，训练积极性减弱，或者课程安排导致当天练习不足；如果 `Daily Submissions` 很高但 `Daily AC Rate` 明显偏低，则可能说明当天题目整体较难，或者某些新增题目存在理解门槛较高的情况；如果平均运行时间和内存占用突然升高，则有可能反映出学生普遍开始提交更复杂题目，或者出现了需要进一步关注的性能问题。因而，这组指标虽然简单，却为后续图表分析提供了重要入口。

### 6.2.3 30-Day Trend 与 30-Day AC Rate 的用途与意义

`30-Day Trend` 图表主要展示最近一个月内平台每日提交数和每日通过数的变化趋势。该图的用途在于帮助管理员从时间维度观察平台热度是否稳定，以及学生整体参与状态是否发生变化。如果一个月内提交量整体呈下降趋势，则在一定程度上说明学生的使用积极性可能有所减弱；如果某些时间段提交量显著波动，则说明存在课程安排、实验任务集中、阶段性训练或考试节点等因素影响。与此同时，通过将提交数与通过数放在同一图表中进行比较，管理员还能够初步判断某些时间段是否存在“提交多但通过少”的异常现象，这通常意味着当时题目难度偏大、学生对相关知识点掌握不牢，或者训练内容突然变化导致适应成本上升。

与之配套的 `30-Day AC Rate` 图表则更直观地展示最近一个月内通过率的变化情况。与同时观察提交数和通过数相比，通过率折线更适合直接判断平台整体训练质量的变化。例如，若某几天的 AC Rate 持续偏低，则说明学生在这几天的整体完成效果不佳，管理员可以进一步回溯对应日期新增的题目内容、教学安排或训练主题，从而决定是否需要向任课教师反馈情况，帮助教师及时跟进学生状态。可以说，`30-Day Trend` 强调“数量变化”，而 `30-Day AC Rate` 更强调“完成质量变化”，两者结合之后，能够较完整地反映平台最近一个月的整体运行状态。

### 6.2.4 Language Distribution 与 30-Day Language Trend 的用途与意义

`Language Distribution` 图表用于展示某一天各编程语言的使用占比及对应通过率。该图表的用途在于帮助管理员观察学生在编程语言选择上的偏好结构，以及不同语言下的解题表现差异。若某种语言的使用人数明显偏少，可能意味着学生对该语言掌握不足，或在做算法题时缺乏信心，因此倾向于使用自己更熟悉的语言；若某种语言的使用率较高且 AC 率也较高，则说明学生在该语言上的熟练程度较好，能够较为稳定地完成题目。通过对不同日期的该图表进行横向比较，还可以进一步观察学生语言使用习惯是否随着课程推进而发生变化。

`30-Day Language Trend` 图表则从趋势角度展示一段时间内不同语言使用情况的变化。与单日的 `Language Distribution` 相比，该图能够更加直观地反映某种语言是否逐步被更多学生使用，或者是否出现明显下降。例如，若 Python 使用量持续增长，可能说明学生在完成中低难度题目时更倾向于选择开发效率较高的语言；若 C++ 仍然保持较高占比，则说明学生在算法训练中仍较依赖其标准库和性能优势。该图的意义在于，它能够辅助教学管理者判断学生群体在编程工具使用上的整体倾向，从而为课程安排、实验指导和语言教学重点提供参考。

### 6.2.5 Verdict Distribution 与 30-Day Verdict Trend 的用途与意义

`Verdict Distribution` 图表用于展示某一天平台判题结果的分布情况，包括 AC、WA、RE、CE、TLE 等。该图的主要用途是帮助管理员快速识别“当天学生最主要的问题是什么”。例如，如果某一天 `WA` 占比明显偏高，则说明学生主要问题在于算法逻辑、边界条件或输出格式处理不当；若 `CE` 占比较高，则可能意味着学生在语法、语言细节或环境使用方面仍不熟悉；若 `RE` 或 `TLE` 比例偏高，则可能说明学生在程序健壮性、时间复杂度或输入处理上存在问题。与单纯查看 AC 率相比，该图表可以更细粒度地定位错误类型，有利于管理员或教师在课后进行针对性跟进。

`30-Day Verdict Trend` 图表则将这种错误结构扩展到最近一段时间内进行观察。它的意义在于，可以让管理员更直观地看到学生群体在不同时间段内主要出现的是哪一类判题错误。例如，若最近一段时间 `CE` 持续较多，可能说明学生刚接触新的编程语言或开发环境；若 `TLE` 在某阶段明显增加，则可能意味着题目开始涉及更高复杂度算法，学生在时间复杂度控制上压力增大；若 `WA` 持续较高，则可能反映算法思路和边界处理方面存在普遍问题。相比单日的结果分布图，该趋势图更强调“变化”，更适合观察教学阶段性特征。

### 6.2.6 Hourly Activity 的用途与意义

`Hourly Activity` 图表用于展示某一天不同小时段内的提交量、通过量和活跃用户数。该图的用途主要体现在系统运行管理和资源预留两个方面。首先，通过该图可以观察某一天的访问高峰时段。例如，如果晚间某几个小时的提交量和活跃用户数显著升高，则说明该时段是学生集中练习和提交代码的高峰期。对于平台管理员而言，这类信息有助于判断未来同类型时段是否需要预留更多的系统资源，以避免在高峰时段出现评测排队、容器竞争或响应变慢的问题。

其次，小时活跃度图也能反映学生的学习习惯和训练节奏。若高峰主要集中在课后时间段，说明平台更多承担自主训练功能；若白天特定时间出现集中高峰，则往往与课程实验或教师统一布置任务有关。该图因此不仅是一个运维指标，也具备一定的教学行为观察意义。

### 6.2.7 Problem Verdict Breakdown 与 Top Problems 的用途与意义

`Problem Verdict Breakdown` 图表针对某一天最热门或指定题目，展示该题对应的判题结果细分情况。该图的用途在于帮助管理员将全站分析进一步聚焦到具体题目层面。若某道热门题的 `WA` 比例远高于其他结果，可能说明学生在算法思路或边界处理上普遍出错；若 `RE` 或 `TLE` 比例较高，则说明题目的实现难点更偏向程序鲁棒性或复杂度控制。管理员可以结合题目内容、测试数据和错误类型，对题目可能存在的问题进行判断，例如题目是否过难、题面是否表达不够清晰、是否需要增加提示或与教师沟通进一步干预。

`Top Problems` 表格则用于展示当天提交量最高的题目排行，并同时给出 AC 率、平均时间和平均内存等信息。其意义在于帮助管理员识别平台中真正被广泛使用、被反复练习或被普遍卡住的题目。一个题目如果提交量很高但 AC 率较低，说明它既受关注又有一定难度，是管理员重点关注的对象；如果提交量很高且 AC 率也较高，则说明该题具有较好的练习价值和适中的难度。通过这两种展示方式结合，管理员能够兼顾“题目热度”和“题目质量”两个维度。

### 6.2.8 Top Users 的用途与意义

`Top Users` 表格展示某一天提交量最高的用户及其通过率。该图表的用途主要是观察平台中最活跃的学生群体，并结合 AC 率判断其做题效果。对于管理员而言，这一信息可以帮助识别出哪些学生训练积极性较高，哪些学生在高提交量的同时仍保持较高通过率，说明其学习状态较好；若某些用户提交量很高但 AC 率偏低，则也可能意味着其正在高强度练习但掌握仍不稳定。虽然该图不直接用于评价学生优劣，但它能够为教师和管理员提供一个活跃度观察视角，有助于后续进行有针对性的教学关注。

### 6.2.9 管理员页面综合应用价值分析

总体来看，管理员侧 `System Analytics` 页面通过概览卡片、趋势图、分布图和明细表的组合，实现了从“平台整体状态”到“具体问题定位”的逐层分析。其综合价值主要体现在以下几个方面。第一，它能够帮助管理员判断平台活跃度与学生整体参与情况是否稳定；第二，它能够识别某一时间段学生常见错误类型，从而为教师调整教学节奏或课后讲解提供依据；第三，它能够揭示平台的高峰时段和潜在资源压力，为系统运维提供支持；第四，它能够帮助管理员观察题目热度与题目难点，提升题库管理质量。因此，管理员页面不仅是数据展示界面，更是在线判题系统向教学管理和平台运营延伸的重要体现。

## 6.3 普通用户个人分析页面设计与应用价值

### 6.3.1 页面总体设计

普通用户侧的 `My Analytics` 页面主要面向学生个人使用，目标是帮助用户通过数据回顾自己的做题过程、发现学习节奏变化并识别主要错误类型。相较于管理员页面强调“全局观察”，用户页面更强调“个体反馈”，其图表内容围绕个人提交行为展开，包括个人提交趋势、个人通过率变化、语言使用习惯、判题结果分布以及题目掌握情况等。\n\n从学习反馈角度看，单纯展示一次提交的判题结果只能告诉学生某一次代码是对还是错，而无法帮助其理解较长周期内的学习状态变化。通过将个人的历史提交数据组织成图表，用户可以看到自己在一段时间内的活跃程度、稳定程度和薄弱点，从而形成连续性的自我评估。这也是 `My Analytics` 页面存在的根本意义。

### 6.3.2 30-Day Submission Trend 与 30-Day AC Rate 的用途与意义

`30-Day Submission Trend` 图表展示用户最近一个月的每日提交数和每日通过数。它的用途在于帮助学生观察自己的学习节奏是否稳定。例如，若某些时间段几乎没有提交记录，则说明这些时间段练习较少，可能存在学习懈怠；若某些时间段提交数较多但 AC 数较少，则说明在这些时间段内虽然做题较积极，但完成效果不理想，可能反映出该阶段遇到的题目更难，或者学习状态不够稳定。相比只记忆“自己最近做了很多题”这种主观印象，趋势图可以用可量化的方式帮助学生进行更准确的回顾。

与此相对应的 `30-Day AC Rate` 图表则用更直观的方式展示个人通过率随时间变化的情况。其意义在于帮助学生从“质量”维度观察自己的学习状态。有时用户的提交数并不低，但 AC Rate 可能持续下降，这说明其近期虽然在练习，但解决问题的效率和准确性有所下降；反之，如果提交量稳定而通过率逐步提高，则说明学习效果正在改善。因此，这一图表能够作为学生自我反思的重要依据，帮助其及时调整学习节奏和题目选择策略。

### 6.3.3 Language Distribution 与 Daily Language Activity 的用途与意义

`Language Distribution` 图表用于展示用户在不同语言上的使用占比及通过率。它的用途在于帮助学生认识自己在语言选择上的习惯。例如，有些用户可能几乎总是使用某一种语言完成提交，这说明其对该语言更熟悉；若某些语言使用次数较少，则可能说明学生在这些语言上的掌握不够充分，或者在写算法题时缺乏自信。通过率信息则进一步反映了用户在不同语言上的解题表现，从而帮助其判断自己是否真正熟练掌握某门语言，而不是仅仅“偏好使用”某门语言。

`Daily Language Activity` 图表则从趋势角度展示用户在不同日期对各种语言的使用情况。与单一的语言占比图相比，这种趋势图更能体现用户语言使用习惯是否发生变化。例如，用户可能在某一阶段开始尝试更多地使用 Java 或 Python，这反映出其技能练习方向的变化。该图的意义在于帮助学生观察自己在语言能力培养方面是否更加均衡，同时也能够为其后续学习规划提供依据。

### 6.3.4 Verdict Distribution 与 Daily Verdict Activity 的用途与意义

`Verdict Distribution` 图表展示用户个人提交结果的总体分布情况。它的主要用途是帮助学生识别自己最常见的错误类型。如果 `WA` 占比较高，说明主要问题可能是算法思路或边界处理；若 `CE` 较多，则表明语法与语言细节掌握仍需加强；若 `RE` 或 `TLE` 较多，则说明程序鲁棒性、复杂度分析或输入处理存在不足。相比单次提交的错误反馈，这种分布图能够帮助学生从整体上认识自己的问题类型，更利于有针对性地提升能力。

`Daily Verdict Activity` 图表则展示不同日期下各类判题结果的变化情况。其意义在于帮助学生回顾“自己在哪些时间段错误特别多”，从而进一步判断当时是否是因为题目难度突然增加、学习状态不佳，或者缺少系统复盘。例如，若某几天 `WA` 显著上升，则说明当时的练习重点可能集中在逻辑较复杂的题目上；若某段时间 `CE` 增多，则说明语言使用存在生疏情况。通过这种时间化的错误回顾，学生能更清晰地认识自身问题是长期性的还是阶段性的。

### 6.3.5 Problem Stats 的用途与意义

`Problem Stats` 表格用于展示用户在已经做过的题目中的提交次数、通过次数和 AC 率等指标。与趋势图和分布图相比，这一部分更强调题目级别的掌握情况。其用途在于帮助学生查看自己在哪些题上提交较多、通过率较低，从而识别哪些题目自己真正掌握，哪些题目仍然处于“反复尝试但尚未稳定解决”的状态。对于学生而言，这种题目层面的统计有助于后续复习和查缺补漏，也能帮助其判断是否需要重新回顾某些知识点或典型题型。

从学习反馈意义上看，`Problem Stats` 是用户页面中最接近“学习成果记录”的模块。趋势图可以反映节奏，分布图可以反映结构，而题目统计表则直接反映具体训练对象的完成效果。因此，这一模块与前面的趋势和分布图共同构成了较完整的个人学习画像。

# 第七章 总结与展望

## 7.1 全文总结
本文围绕“基于大数据计算引擎的在线判题系统的设计与实现”这一课题，完成了一套从在线判题到离线分析再到预测评估的综合系统建设。系统以 Spring Boot 和 MySQL 为业务基础，以 Docker 为安全判题执行环境，以 Hadoop HDFS 作为历史日志存储载体，以 Hive 完成基础聚合与描述性分析，以 Spark 实现提交量预测和题目难度评估，并通过 React 前端完成管理员和普通用户的数据可视化展示。

从实现结果看，系统已经具备完整的业务闭环：普通用户可以完成注册、登录、查看题目、提交代码和查询结果；管理员可以完成题目与测试用例管理、判题日志导出、系统统计查看、预测结果查看以及题目难度评估查看。同时，系统还构建了清晰的数据流路径，即从判题结果生成分析事件，再导出到 HDFS，借助 Hive 与 Spark 完成统计和预测，再将结果回写 MySQL，最终通过后端 API 和前端页面实现展示。这一设计使在线判题系统从单纯的业务执行平台升级为具备数据分析与预测能力的综合平台。

从课题意义看，本文的工作表明，将大数据计算引擎引入在线判题系统具有较高可行性。Hadoop 与 Hive 适合承担历史数据沉淀和离线聚合任务，Spark 适合承担更复杂的预测和评估计算任务，而 Spring Boot 与 MySQL 仍然负责在线业务和结果查询，形成“在线业务与离线分析解耦、结果统一回流”的工程架构。这种设计思路不仅适用于当前的教学训练场景，也具有一定的推广价值。

## 7.2 系统特色与创新点总结
结合全文实现内容，可以将本系统的特色与创新点概括为以下几个方面。

第一，系统在传统在线判题功能基础上，进一步构建了基于 HDFS、Hive 和 Spark 的大数据分析链路，使判题日志不再只是业务副产物，而是成为可持续利用的数据资产。

第二，系统采用 Docker 容器沙箱执行用户代码，结合网络禁用、资源限制、只读挂载等策略，形成较为完整的安全判题执行方案。

第三，系统不仅提供基础统计和描述性分析，还实现了 Spark 提交量预测和题目难度评估两个面向管理决策的离线模块，体现了大数据计算引擎在在线判题场景中的进一步应用。

第四，系统将离线分析和预测结果通过 MySQL 回写并在前端页面中可视化展示，实现了分析结果的产品化落地，使管理员和普通用户都能够直接从页面获得决策信息。

## 7.3 存在的不足
尽管本文实现的系统已经完成了题目要求中的主要目标，但仍存在一些不足。

第一，判题任务目前采用单体应用中的异步 worker 实现，适合中小规模环境，但在更高并发场景下，可能需要进一步拆分判题服务并引入消息队列或分布式调度机制。

第二，Hive 与 Spark 分析任务目前主要依赖手动或脚本触发，自动化调度能力仍有提升空间。若后续采用 Airflow 或更完善的任务编排工具，可以进一步提高离线分析链路的自动化水平。

第三，提交量预测模型目前较为简单，主要用于验证预测链路是否可用，尚未引入更多时间序列特征和评价指标。题目难度评估同样以规则模型为主，虽然解释性强，但在精度和适应性方面仍有提升空间。

第四，前端页面虽然已经具备分析与预测展示能力，但界面美观性、交互深度和移动端适配仍有改进余地。

## 7.4 未来展望
针对上述不足，后续可以从以下几个方向继续完善系统。

第一，进一步扩展 Spark 预测与分析能力。例如引入活跃用户预测、题目热度预测、小时级负载预测，甚至基于用户行为数据构建用户画像和个性化推荐模型。

第二，完善题目难度评估方法。当前的规则型难度评估适合作为第一阶段方案，后续可以结合更多特征，如题目标签、提交语言差异、长期历史趋势和早期提交表现，引入监督学习或聚类方法，提高难度评估的精度与解释能力。

第三，优化系统架构。可以考虑将判题服务从主应用中拆分出来，形成更独立的判题节点体系，并通过消息队列提高任务分发效率；同时增加更细粒度的监控、日志追踪和异常告警能力。

第四，丰富可视化与产品能力。后续可将管理员页面进一步扩展为综合运维与教学分析平台，为教师、管理员和学生提供更加个性化的数据展示。

综上所述，本文完成的在线判题系统已经实现了从业务系统到数据分析平台的初步升级。虽然仍有一些值得继续深入的方向，但当前系统已经具备较强的完整性和较好的研究价值，为在线判题系统与大数据计算引擎的结合提供了可行思路。
